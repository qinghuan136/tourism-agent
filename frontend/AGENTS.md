# Tourism Agent 前端开发约定

本文件适用于 `frontend/` 及其子目录，并继承仓库根目录 `AGENTS.md`。这里只记录前端特有约束；发生冲突时，以本文件中更具体的前端规则为准。

## 1. 当前范围

前端只实现现有旅行 Agent 垂直链路的用户界面：

- 检查 API 运行状态；
- 发送消息并展示普通对话；
- 展示运行中、等待用户补充信息和取消状态；
- 独立展示候选行程与当前行程；
- 让用户明确确认或拒绝候选行程。

当前不实现登录、用户与旅行管理、真实预订、支付、订单和退改签。新增这些能力前必须先确认后端阶段与接口契约，不能只在前端伪造流程。

## 2. 固定技术栈

- Vue 3 + TypeScript；
- Pinia 管理跨组件业务状态；
- Vue Router 管理页面路由；
- Element Plus 提供基础交互组件。

不得擅自改用 React、增加第二套状态管理或组件库。当前固定使用 pnpm 和 Vite，只保留 `pnpm-lock.yaml`，不混用 npm、Yarn 或 Bun 安装命令。

## 3. 代码边界

前端落地后按职责组织，而不是按页面堆积所有逻辑：

- `src/api/`：HTTP 请求、响应解析和后端错误映射；
- `src/stores/`：Pinia 业务状态和确定性状态转换；
- `src/router/`：路由表与必要的路由守卫；
- `src/views/`：路由级页面，只负责编排页面区域；
- `src/components/`：可复用、职责单一的展示或交互组件；
- `src/composables/`：确有复用价值的组合式逻辑；
- `src/types/`：前端共享类型与 API 契约类型。

组件不得直接散落调用后端；调用统一经过 `src/api/`，跨组件流程统一经过 Pinia。不要把临时 UI 状态全部塞入全局 Store，也不要为单一用例提前创建通用框架、注册中心或包装层。

## 4. API 交互不变量

以 `docs/api-contract.md` 为唯一接口依据，不凭 UI 需要猜测后端行为。

- 每个新用户意图生成新的 UUID `idempotency_id`；网络重试同一请求必须复用原值和完全相同的请求体。
- 请求运行期间禁止发送另一条用户消息；禁用发送入口，并提供取消操作。
- `202 processing` 保持原请求的等待状态；不要自动生成新幂等键重复执行。
- 取消后废弃本地等待状态；下一条消息是新请求，必须生成新的幂等键。
- `message` 只进入普通对话区域。
- `candidate_itinerary` 必须在独立候选区域完整展示；存在候选时只允许通过明确按钮发送精确的“是”或“否”。
- `current_itinerary` 必须在独立的当前行程区域展示，不复制进对话气泡。
- `route` 仅表示最近完成或当前中断的业务模块，不把它解释成整轮只执行过一个模块。
- 面向用户的错误提示应保留可执行动作，例如重试、取消或返回旅行选择；不得暴露堆栈和内部异常。

## 5. UI 开发流程

新建页面、主要界面或整体重设计时，先使用 `frontend-app-builder` 形成完整视觉方案并获得用户确认，再用 Vue 技术栈实现；该技能的 React 默认值不适用于本项目。

- 先明确完整页面、关键状态、桌面与移动端延续方式，不只设计首屏。
- 从确认后的方案提取颜色、字体、间距、圆角和组件变体，集中为可复用 token。
- 优先复用 Element Plus 的可访问交互能力，通过主题 token 和明确的局部样式适配视觉方案；不要复制其内部实现。
- 用户可见文案使用中文；TypeScript 标识符、类型名和组件名使用英文。
- 保持语义化结构、键盘可操作、可见焦点、合理对比度，并尊重 `prefers-reduced-motion`。
- 不使用静态截图冒充交互界面，不提交占位按钮、假进度或无法工作的控件。

## 6. TypeScript 与状态设计

- API 请求和响应必须有明确类型，不使用 `any` 绕过契约。
- Store 只保存客户端恢复界面所需的状态；后端的 Conversation、候选行程和当前行程仍是权威数据。
- 将运行中、等待补充信息、等待候选确认、已取消和失败等状态显式建模，避免由多个布尔值组合出矛盾状态。
- 组件 Props、Emits 和公共函数必须有明确类型；优先使用组合式 API 与 `<script setup lang="ts">`。
- Element Plus 组件的二次封装必须解决真实复用或领域语义问题，不为改名而包装。

## 7. 测试与验收

前端实际命令如下：

```powershell
cd frontend
pnpm install
pnpm dev
pnpm build
pnpm typecheck
pnpm lint
pnpm test
```

行为变更必须覆盖相应测试，重点包括 API 适配、幂等键、Pinia 状态转换、候选确认和取消流程。不要只测试组件是否挂载。

渲染后的调试与验收使用 `frontend-testing-debugging`：

1. 优先使用 Browser 检查真实页面；仅在 Browser 不可用且任务允许时使用 Playwright。
2. 验证页面身份、非空渲染、无框架错误遮罩和无相关控制台错误。
3. 至少执行一次核心交互并检查状态变化。
4. 视觉变更同时检查桌面和一个移动端视口，关注溢出、遮挡、换行、焦点和加载状态。
5. 若实现来自确认后的视觉方案，使用截图逐项核对文案、布局、字体、颜色、间距和响应式行为。

交付前运行前端自身的 build、typecheck、lint 和 test；涉及前后端契约时，同时运行仓库根级 `AGENTS.md` 指定的后端测试与静态检查。

## 8. 维护原则

技术栈、目录职责、API 契约或验证命令发生变化时同步更新本文件。只记录长期有效且可执行的约束；临时任务说明、设计草稿和一次性排障记录放到对应任务文档，不持续膨胀 `AGENTS.md`。
